Choose an application

StatePort calls the things you work in applications. Each one is a folder of plain files with a name, a history, and a set of actions. There are two ways to get one:

  • Open the bundled study sample. It is a small study-plan app that ships with StatePort, and it is the fastest way to see how the loop works.
  • Import a template. You give StatePort a Git repository, and it makes your own copy of it. Templates explains how that works and which templates are available.

Importing makes a separate copy with its own history. The repository you imported from stays where it is, and StatePort does not change it.

Two kinds of action

Every application offers two kinds of action, and the difference between them matters.

  • Check actions. These read the files of the application and give a verdict: passed, not yet, or invalid, with the reason. They change nothing, and no model is involved. The verdict comes from a check that the template ships, and it runs in a sandbox.
  • Agent actions. These ask a model to do a piece of work on your application. The model works on a copy, and what it produces is a proposal for you to look at.

Both kinds leave a record that you can read later.

Agent actions: the model works on a copy

When you start an agent action, StatePort:

  1. makes a copy of your application and gives that copy to the model;
  2. runs the model inside a sandbox where it can see the copy and nothing else on your machine;
  3. lets it reach only the model provider's addresses on the network;
  4. compares the copy with the original once the model stops.

Your own files are not touched while the model works. The result is a proposal, and it has three parts:

  • the exact changes, as a diff, so you can read them line by line;
  • the check's verdict before the change;
  • the check's verdict after the change.

If the model tried to write a file it was not allowed to write, the proposal is refused instead of shown to you.

Review and apply

You decide. Two buttons are offered: Apply and Reject.

  • Apply makes the change in your application as one commit in its history. You can see exactly what changed, and undo it by hand if you want to.
  • Reject throws the proposal away and leaves your application as it was. Rejecting is normal and costs you nothing.

Only apply a proposal you have read. The diff tells you what the model believes about your work; the check tells you whether the files agree with each other. Neither replaces your judgement.

Chat

Chat answers questions about an application. That is all it does.

  • It never runs tools.
  • It never changes a file or a setting.
  • A chat message is not saved as work in your application. If you want a change, use an action.

Chat needs a model. Models and keeping up explains how to get one, including a route that needs no account at all.

A daily loop

  1. Open the application and read its current state.
  2. Run its check action. If the verdict is not yet, the reason tells you what is missing.
  3. Ask for one small thing with an agent action.
  4. Read the proposal: the diff, and the check before and after.
  5. Apply it or reject it.
  6. Read the record of what happened. Read a change record walks through one.

Each application has its own actions:

  • ProjectState offers Set up project (from your own words), Do the next action and Check.
  • StudyState offers Set up study, Plan next session and Check.
  • Decision Log offers Check, List due, Draft the oldest open decision and Add an open question.

Templates describes what each one does.

Backup

Every application has a Back up now button. A backup is a copy of the files of that application. Restoring one creates a new application from the backup; it does not overwrite the application you already have. Backup and recovery has the details.
