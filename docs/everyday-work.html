Choose an application

After installation, the application home shows installed applications and recent activity. To add one, open Catalog. A reviewed sample such as StudyState can be installed there, or choose Import a repository for a committed ProjectState, StudyState, or valid StateSpec template. Catalog is a reviewed shelf; it is not a marketplace.

For an import, StatePort inspects the repository without executing its code. Review the detected type, branch, exact commit, working-tree status, and findings. Approve that inspection, name the application, and choose Create isolated copy. If the source changes after inspection, inspect it again; a stale approval is refused. The source repository remains untouched.

A first session with the StudyState sample

Use the reviewed StudyState sample as a small, concrete loop. In Catalog, choose StudyState, review what it needs, and install the instance. Open it and begin the suggested activity. Start activity first opens a review showing the activity and the exact change from not started to in progress. Choose Approve Start only when it matches your intention.

After the apply succeeds, the activity is in progress. Pause it, choose another activity, or write a reflection. A reflection begins as a browser draft. Review its exact effect before saving it as evidence: the sample marks the activity completed and saves the reflection when you choose Approve and apply. The saved facts you should expect are the activity status and the reflection associated with this StudyState application; the reflection remains self-reported and is not independently verified learning.

Open Receipts and inspect the applied change. Then reload the page and reopen the same StudyState instance. The activity status and reflection should still be present because they belong to the durable application state. If the result is absent, stop and inspect the receipt and recovery status before retrying.

For a normal daily session, use this same loop: read the current goal or next activity, request one bounded change, review it, apply it, inspect the receipt, and continue from the saved state next time. Some applications expose conversation proposals, while the optional development Workbench exposes a governed run path. Controls are capability-gated: a missing control means that application or release does not provide that operation.

Check readiness before you ask

Use Workspace readiness as a set of observations, not as a single green light. It separates Local service, Execution runtime, Worker execution, Provider, and Applications. A connected service does not prove that a provider is authenticated or that a request can succeed.

Open Set up or verify provider when the provider row needs attention. Current controls can show the selected provider, executable status, model configuration, StatePort connection, login presence, bounded-request result, and unavailable billing/quota information. A platform operator can select Codex or OpenCode and save a model identifier. Saving configuration is not authentication. For Codex, open Show installed login command, paste the displayed command into the Ubuntu WSL terminal, follow the one-time browser code flow, return to StatePort, refresh status, and choose Verify bounded request. The check is short and may use account quota; it does not send an application conversation or files. OpenCode selection is recorded, but execution is not available through this path.

When work needs review

StatePort keeps request, review, approval, apply, validation, and receipt distinct. A proposal may be useful even when you reject it. Approval grants only the reviewed operation and is rechecked against the current base, policy, permissions, side-effect class, and budget.

For running work, Cancel asks to interrupt the selected operation; in-progress output may be incomplete and cancelled work is not automatically resumed. For an execution workspace, stopping preserves a reusable workspace while cancellation can leave the workload terminal. Read the confirmation text and the listed reversibility before confirming.

Receipts and recovery

Open Receipts from the application or the application overview to search and inspect durable operation records. A receipt answers what was requested, which actor acted, what changed, which checks ran, and what remains uncertain. It is evidence of an operation, not proof that the result is correct. Receipt details may include a diff, exact record, verification status, and raw JSON; export is available where the installed surface exposes it.

If an application workspace is missing or interrupted, open the execution host details and choose Recover application workspace when it is offered. Recovery reuses the sealed profile and grant and reattaches preserved data; it does not overwrite existing or partially initialized data. If provider work is stuck, Disconnect StatePort stops the active assistant processor and cancels queued requests while keeping the transcript; reconnect only after reviewing readiness.
