Availability boundary The deployment foundation runs inside the private local alpha on Linux with rootless Podman. This page describes what is implemented there; availability lives in the release ledger.

What a governed deployment is

StatePort treats a deployment as durable state, not as a command someone once ran. Plans, approvals, accepted revisions, observations, transitions, and receipts remain StatePort records even when the container runtime is absent. Podman is a replaceable execution adapter: it performs bounded operations and reports what it observed — it is evidence, never the source of truth.

How a deployment happens

  1. Inspect. StatePort reads the project without changing it, bound to the exact committed source — never an uncontrolled working tree.
  2. Plan. The inspection becomes an exact, versioned plan: services, images, ports, storage, and generated configuration, in one reviewable document.
  3. Approve. You approve the plan by its digest. Change any part of the plan, the source, or the target, and the approval no longer applies.
  4. Apply and verify. The adapter builds and starts the deployment on local rootless Podman with deterministic names and ownership labels, then waits for the declared health checks before calling it healthy.
  5. Operate. Status, logs, and restart stay observable afterwards; an interrupted operation is reconciled from its records rather than silently replayed.
  6. Remove, or purge. Ordinary removal stops the runtime but keeps the named data volumes. Purging the data is a separate plan with its own exact approval.

Every transition produces a receipt, and receipts are hash-chained: a failed or interrupted step stays visible instead of being retried blindly.

What the plan refuses

The alpha contract deliberately refuses deployment shapes it cannot govern safely: root containers, privileged or host namespaces, host bind mounts, mutable image tags, missing health checks, plaintext secret-like configuration, and exposure beyond the loopback interface. A refusal is a recorded outcome, not an error to work around.

What is not supported yet

  • Upgrade and rollback between deployment revisions — planned for a later slice; today, changing a deployment means a new reviewed plan.
  • Remote hosts over SSH, image-registry distribution, and a dedicated deployment interface.
  • Arbitrary projects. Support is limited to projects that satisfy the documented deployment contract, plus reviewable assisted proposals for recognizable Python, Node, and static-web repositories.
  • Cloud or public-network deployment, including Azure. The current target is a single local machine.
