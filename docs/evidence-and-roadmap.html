Claims should grow only as their evidence grows.

A screenshot, a passing local test, a hosted CI run, and a human review are different kinds of evidence. StatePort keeps those states separate.

Reading guide This page explores the model. Availability lives in the release ledger.

Six useful evidence states

implemented → automated validation → exact-runtime agent validation → human validation → human acceptance → remote closure → released

These states do not collapse into one another. Automated tests can pass without proving the interface works. An agent journey must bind source, runtime, instance, actions, durable results, and uncertainty. Human validation assesses usability and trust; human acceptance is an explicit decision on one exact candidate. Remote CI and a release remain separate again.

Report a problem during the local checkpoint

The local StatePort candidate includes an in-product Report a problem control. Describe what you expected and what happened, optionally attach the current screenshot, then review the captured route and runtime context before saving. The report stays in the local StatePort evidence store for operator review; it does not upload itself, open a public issue, launch an agent, or change product source.

  • Include the candidate/build identity and application instance when they are visible.
  • Never include passwords, tokens, private conversation text, learner data, or unrelated files.
  • If the control is unavailable, record the same facts in the private owner-test notes and mark the reporting path itself as failed.
  • No public support or vulnerability intake route is active yet; security reports need a separately activated private route before external testing begins.

What is public today

This website brings together the documentation, prototype, paper, and release ledger. Software availability is recorded separately, with its exact source and evidence.

What remains open

  • A public source release, licensing decision, artifacts, and verified install path.
  • Human validation and acceptance of the exact local product candidate.
  • Independent validation of an exact delivered source and its packaged runtime.
  • Canonical upstream release acceptance for application packages.
  • External-user and human product acceptance.
  • Controlled evaluation before any comparative or performance claim.

How to evaluate the model

The central questions are testable: does explicit state improve recovery after a session loss? Do digest-bound approvals reduce mismatch? Do receipts improve a person’s understanding of change? Does host replacement preserve more useful continuity than a transcript export? A credible answer needs baselines, repeated runs, and measures that can falsify the claim.
