Documentation / Updates

An update is a change you approve, like any other.

This page describes the update contract shipped with the published v0.1.0-alpha.5 candidate. The public release remains an alpha candidate, and every update is still approval-gated and health-gated.

Alpha.5 installation temporarily disabled v0.1.0-alpha.5 remains signed, published, and byte-intact, but its public install path is fail-closed after the owner-reported failed partial first-host bootstrap. No clean-install receipt, human acceptance, or independent security review exists; see the release ledger.

Exact releases, pinned by digest and signed

An update starts from an exact, versioned release — never a moving “latest”. The candidate's images are bound to immutable digests, so what you approved is bit-for-bit what runs. The release index (stateport.release-index/v1) and the image set carry pinned-public-key Cosign signatures under the StatePort alpha release key, with SPDX SBOMs and vulnerability-scan dispositions alongside. Tampering with any signed field, image digest, or artifact refuses the install or update. For this private candidate the signatures are not uploaded to a public transparency log; verification relies on the pinned public key and its recorded fingerprint.

A pinned trust root that never rotates itself

At install time the installer pins the release trust root out of band and stores it durably. Every successor release is verified against that pinned root — never against the candidate artifact itself. Trust-root rotation is a manual operator act through the same out-of-band path: a release artifact can never rotate trust in band, and a successor signed by a different key is refused as an untrusted signer.

Approval before application

Updates follow the same governance rule as every other consequential change: StatePort proposes an exact change, you review it, and only an explicit approval lets it proceed. The alpha default update policy is notify — StatePort tells you an update exists and does nothing further. Applying an update requires an exact authorization bundle; automatic application is opt-in and remains health-gated.

Health-gated, with automatic rollback

Apply installs the successor, waits for health checks to pass, and only then treats the update as successful. If the successor is unhealthy, the updater rolls back automatically and the predecessor is retained. The full line — status, policy, check, plan, authorize, apply, rollback, and reconcile — is driven through the stateport-update wrapper the installer writes.

Receipts either way

Installed, applied, refused, and failed updates all leave receipts. A failed update stays visible as a failed update; it is never silently retried, because retrying an operation with unknown external effects can do more harm than the original failure.

What this does not change

  • Alpha.5 is published only for its exact WSL2 Ubuntu 24.04 AMD64 public-test target; its artifacts and current status are on the download page.
  • Signatures for this private candidate are not recorded in a public transparency log.
  • Trust-root rotation stays manual and operator-driven; nothing rotates trust automatically.
  • Human acceptance is pending, and reviews so far are internal multi-agent reviews with independence not established.

The release ledger records when a public release exists, and the limitations page collects every remaining boundary.
