Documentation / Updates

An update is a change you approve, like any other.

This page describes the update design StatePort is being built against. Most of it is not user-available yet — where design and delivery differ, this page says so.

Design, not availability No public release exists, so there is nothing to update today. This is the target contract an update must satisfy before it ships, not a description of a feature you can use now.

Exact releases, pinned by digest

An update starts from an exact, versioned release — never a moving “latest”. The release bundle contract already rejects mutable image tags and uncontrolled provenance: installable material is rendered with image digests pinned, so what you approved is bit-for-bit what runs. Cryptographic signing and provenance attestations are part of the release programme but are not yet established; no signed release index exists today.

Approval before application

Updates follow the same governance rule as every other consequential change: StatePort proposes an exact change, you review it, and only an explicit approval lets it proceed. Automatic background updating is not part of the design — the default posture is that the user decides when a known, described update is applied.

Health-gated, with rollback-or-truthful-refusal

The target update path applies the new version, waits for health checks to pass, and only then treats the update as successful. If health does not pass, the system rolls back to the prior accepted state — or, where a safe rollback cannot be proven, it refuses truthfully and says so instead of guessing. This health-gated update with rollback is an explicit requirement of the alpha acceptance programme; it is not fully delivered in the current candidate, and deployment revisions do not yet support upgrade and rollback.

Receipts either way

Applied, refused, and failed updates all leave receipts. A failed update stays visible as a failed update; it is never silently retried, because retrying an operation with unknown external effects can do more harm than the original failure.

What must exist before this is real

  • A published release with exact versions, release notes, and immutable artifacts.
  • A verified install and upgrade path from a clean supported environment.
  • Delivered upgrade and rollback between revisions, with their receipts.
  • Signing and provenance for the release index and images.

The release ledger records when each of these becomes true.
