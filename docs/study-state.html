StudyState: a template for a study plan

StudyState keeps a learner's targets, evidence, sources and next activity in plain files. StatePort can import a StudyState repository and keep your own copy of it, with its own check and its own actions.

What StudyState is

StudyState is a template for a study plan. It keeps a learner’s targets, activities, sources, sessions, reviews and evidence as readable Markdown and YAML files. You can run it through StatePort, or you can run it without StatePort at all.

StatePort keeps the saved state outside the chat window, so the record of what you did is still there after the conversation is gone. A chat can help you learn, but chat history is not the record. The files are.

The study sample is a worked application that ships with StatePort, so you can try the loop before you import anything.

The three actions

Once a StudyState application is open, it offers three actions.

  • Set up study. You describe your subject and your goals in your own words, and the application builds the starting files from that description: your profile, your targets and your next action. It works on a copy, so you see the whole change before anything is written. Apply it if it says what you meant, or reject it and try again with clearer words.
  • Plan next session. The application looks at your targets, your sources and what you have done so far, and proposes what to do next. The proposal is a diff: the exact lines that would be added or changed, with the check’s verdict before and after. Apply it and it becomes one commit in the application. Reject it and nothing changes.
  • Check. This runs the check on your files. It answers passed, not yet, or invalid, and tells you why. It is deterministic: it reads the files and compares them with each other. It never asks a model and never changes anything.

Two of the three actions need a model, so they need an AI route. Models and keeping up explains how to get one, including a route that needs no account. The check works either way.

Reflection becomes a change you review

A reflection is your own account of what you did. It is written as a draft first, and you see its exact effect before it is saved: which activity it marks, and what it records as evidence. Apply it only if it matches what you meant to record.

The saved reflection is your own account. It is not independently verified progress, and nothing in StatePort turns it into one.

Choosing the next activity

The next-activity engine belongs to the StudyState template, not to StatePort. In the template’s own design, the engine can pick a question, a spaced review, a paper exercise, a lab, an outside resource, interview or presentation practice, a voice note, a diagram, or an upload-and-review task. Due reviews stay visible. For subjects that change fast, it asks for fresh source information before it asks a question.

In StatePort, Plan next session is what brings that thinking to you as a proposal. You still decide whether it is right for today.

Saved state and restarts

Because the state is in files, it survives: reload the application, reopen it, and your targets, evidence and next action are still there. The same is true after the services restart, and after the Ubuntu distribution restarts.

Whether StatePort stays reachable after you close the last Ubuntu window is handled by a Windows task that keeps Ubuntu running; what happens after a Windows restart has not been measured yet:

Back up before upgrades or big edits, and keep your learner data when you apply template improvements. Backup and recovery has the details.

What StudyState does not do

  • It does not treat source coverage or one easy answer as proof you are ready.
  • It does not call information current without fresh source information.
  • It does not install dependencies or change system settings without your consent.
  • It does not put your data in the public template or in a public repository.
  • StatePort does not give a StudyState file free rein as an agent. The permissions you gave decide what it can do, and the model works on a copy.

Use StudyState

Try the sample

  1. Open the study sample from the first screen, or from Catalog.
  2. Run Set up study, or open the sample that is already set up, and read what the check says.
  3. Run Plan next session, read the proposal, and apply it if you agree.
  4. Write a reflection, review its proposed effect, and apply it to save it as evidence.
  5. Open the record of what happened, reload the application, and check that your activity and reflection are still there.

Import the template

Choose Import a repository and give the public address of the template in Public HTTPS repository. In Branch, tag or commit (optional) you can leave the field empty for the default branch, or type a branch, a tag or a full 40-character commit; StatePort resolves it once to the exact commit, and the review screen shows that commit. Or put a Git checkout in /var/lib/stateport/imports. Check the identity, the source commit and what StatePort detected before you create your own copy. The repository is lennertvhoy/StudyState_Template.

Use the repository directly

You can also clone the public template into a new repository of your own, set up the profile and first target, and run its environment check, its setup helper (it asks for consent), its sanity check and its demo replay. Keep the public template separate from your own repository.

For how to prepare a source, see Use a template. For the project tracker template, see ProjectState. For availability, see release status.
