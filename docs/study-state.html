What StudyState is

StudyState is a study brain operated through a coding agent or through StatePort’s managed application. The small StudyState Sample is a worked application used to demonstrate the saved learning loop. An imported StudyState repository is a different application source. StatePort validates it and stores it as an isolated managed copy with an inspection action; the guided flows exist only in the StudyState Sample.

The sample loop is concrete: choose Start on the current activity, review the change from not started to in progress, and approve it. Write a reflection as a browser draft, review its exact effect, including marking the activity completed, then apply it as evidence. Open the receipt to inspect what StatePort recorded. Reload and reopen the same instance: the completed activity and reflection should remain saved. In the sample, the proposed change comes from a deterministic script, not from a model.

The broader repository contract keeps learner profile, study targets, skill map, sources, activities, sessions, reviews, next actions, and evidence in readable Markdown and YAML. A conversation can help you learn, but chat history is not the canonical record.

The Focus default: what to do next, and why

The next-activity engine belongs to the StudyState template and is not surfaced in StatePort. In the StudyState template’s own model, that engine can choose a question, spaced review, paper exercise, lab, external resource, interview or presentation rehearsal, voice note, diagram, or upload-and-review task. Due reviews remain visible, and volatile subjects require fresh source metadata before an authoritative question.

The StudyState Sample offers a fixed set of activities and a small, explicit activity and reflection flow. An imported StudyState does not get the next-activity engine as a StatePort screen; inspect the imported application’s own files and contract.

Lifecycle you control

  1. Template mode: the reusable public mold remains generic and contains no learner data.
  2. Bootstrap mode: a new repository records its origin while you initialize your learner profile and first target.
  3. Learner-instance mode: the repository contains your targets, evidence, sessions, reviews, and next action.

Use the template’s instance creation flow or make a separate learner repository. Do not personalize the public template. Run its sanity gate after setup or state changes.

Reflection becomes a change you review

In the sample, the reflection starts as a browser draft. Before saving it, review the exact activity and evidence effect. Apply only when it matches what you meant to record. The saved reflection is self-reported learning evidence; it is not independently verified progress.

The agent may suggest a change, but canonical state changes only after the reviewed action is applied. The receipt records what StatePort observed.

Undo and change history

One undo exists today: the StudyState Sample can undo its last evidence update. That undo is itself a reviewed change, it restores the prior evidence-bearing state, and it stays tied to the reviewed change and its receipt, so it does not erase the explanation of what happened. Most other changes have no undo, and platform rollback is not supported in Alpha.20.

StudyState keeps session and activity history alongside current projections.

If you are working directly in a repository, inspect the diff and history before repairing state. Keep the evidence that explains why a correction was made.

Saved state and restarts

After the sample flow, reload the application and reopen the same instance, then return to the activity. The expected saved result is that the activity remains completed and the reflection remains present in evidence. The project’s automated test stops and restarts the service and re-reads the saved plan; that has not been run on an installed Alpha.20. On Alpha.20, reachability after the last WSL window closes is measured (after you sign in to Windows); a Windows reboot is not yet measured.

In a repository instance, closing a session does not erase goals, target map, review queue, source registry, or next action because they live in files. Back up before upgrades or broad edits, and preserve learner state when applying generic template improvements.

What StudyState deliberately does not do

  • It does not treat source coverage or one easy answer as confirmed readiness.
  • It does not claim volatile information is current without fresh source metadata.
  • It does not install dependencies or change system settings without explicit consent.
  • It does not personalize the public template or hide private learner data in a public repository.
  • StatePort does not turn a StudyState file into an unrestricted agent. The adapter and installed permissions remain the authority.

Use StudyState

Try the sample

  1. Open the StudyState Sample and choose Start on its current activity.
  2. Review the exact change, then choose Approve Start so the activity becomes in progress.
  3. Write a reflection, review its proposed effect, and choose Approve and apply to save it as evidence.
  4. Open the receipt, reload the application, and confirm the activity and reflection remain present.

Import a template

Choose Import a repository for a public exact commit or local checkout. Review identity, source commit, and what the detected template exposes before creating an isolated copy. The imported repository does not have the sample’s screens or the next-activity engine.

Use the repository directly

Clone the public template into a new learner repository, initialize the profile and first target, then run its environment check, explicit-consent setup helper, sanity gate, and demo replay. Keep the public template separate from a learner instance.

For exact source preparation, see Use a template. For the project-oriented companion, see ProjectState. For availability, see release status.
