Set up a known release

There are three things to keep distinct: StatePort itself, the template that defines an application, and your instance containing the actual work. Replacing the runtime is not a backup of your instance, and importing a newer template is not an update of your existing work.

Check release status before installing. Alpha.16's fresh installation is blocked. For an existing installation, retain its installer receipt and the URL it printed; follow update and uninstall guidance for its recorded resources.

Use the application

  1. Open the intended application and read its current state before issuing another request. Two instances from the same template hold different work.
  2. Choose one concrete task. Readiness indicates whether the application can perform it with the currently configured tools and permissions.
  3. Review a proposed change before applying it. Check the target, affected files or facts, and requested access.
  4. After applying, inspect the receipt and the updated application state. A successful conversation response alone does not establish that a change was saved.
  5. When returning later, reload the application and confirm the last result is still present. Use Activity and Receipts to resolve uncertainty before repeating a request.

The everyday-work guide walks through this cycle; StudyState provides a concrete reflection example.

Update or move

Before changing an installation, record the installed release, the application identity, and the template source revision. Keep a verified backup outside the runtime resources being replaced. Do not treat a template checkout, container image, or conversation export as a complete instance backup.

In-place platform update is not a supported recovery shortcut in this alpha. Read the update boundary before rerunning an installer. An imported template is an isolated managed copy; editing its original repository does not synchronize your instance.

Moving to a different machine also changes the host environment. Tool availability, permission grants, credentials, and reachable services need checking again. The portability guide explains what can travel with your work and what needs new setup.

Back up and recover

Availability: use the backup and recovery controls only when your installed application exposes them. They depend on the application, permissions, and installed version. This is not a workaround for the blocked Alpha.16 installer.

Before a backup

  • Finish or inspect outstanding changes so you know the state you are preserving.
  • Record the application identity and a few facts you expect to recover: for example, the current project slice or your last study reflection.
  • Where available, use Back up now and inspect the resulting backup status and receipt. A backup attempt is not the same as a verified archive.
  • Keep backups private. Archive verification checks integrity; it does not imply encryption, automatic scheduling, or a retention policy.

Restore a separate instance

The supported recovery model creates a new managed instance. It does not overwrite the source application. In versions exposing Settings → Backup & recovery, an operator selects an indexed backup, reviews the restore plan and destination identity, approves that exact plan, then applies it.

  1. Select the intended verified backup. Check which application and point in its history it represents.
  2. Review the proposed new identity and any source-access details. Do not assume previous consent silently transfers to a new instance.
  3. Apply only the plan you reviewed. If it expires or the backup, source, or destination changes, prepare and review a fresh plan.
  4. Inspect the restore receipt and open the new application. Compare the facts you recorded before the backup.
  5. Check tool readiness and permissions separately. Keep the original instance until you have checked the recovered work and chosen which copy to use.

If recovery stops with an uncertain result, preserve the receipt and both instances for inspection. Do not remove the destination or repeatedly apply the restore to make an error disappear. See troubleshooting.

What recovery does not undo

Filesystem recovery does not recall a sent message, reverse a payment, remove a remote deployment, or undo a provider request. Inspect external effects independently before continuing work. A restored file saying “not sent” cannot prove that a message was never sent.

Current availability

The public release page determines installation availability. Controls described here may be absent in an older installation or unavailable for a particular template. Do not use developer commands or manual file replacement to bypass a missing recovery control. Preserve the original work and report the missing capability.
