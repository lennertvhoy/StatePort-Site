Set up a known release

Keep three things apart: StatePort itself, the template that defines an application, and your application, which holds your actual work. Replacing StatePort does not back up your work. Importing a newer template does not update what you already have.

To install, follow getting started. Keep the install receipt and the address the installer printed. Updates and removal says what this release supports for updating and removing StatePort.

Manage the install

The installer leaves a small command at ~/.local/state/stateport-install/bin/stateport. Run it from the Ubuntu window, as your normal user:

~/.local/state/stateport-install/bin/stateport status
~/.local/state/stateport-install/bin/stateport open
~/.local/state/stateport-install/bin/stateport url
  • status shows what is installed and whether the services answer.
  • open opens StatePort in your browser.
  • url prints the address to open, which is useful when you have lost the printed line.

Two more commands remove it: uninstall, which stops the services and keeps your data, and purge, which deletes the data as well and asks you to type a confirmation. Updates and removal explains both.

Use the application

  1. Open the application and read its current state before you ask for anything. Two applications from the same template hold different work.
  2. Run its check. The verdict tells you whether the files agree with each other, and the reason tells you what is missing.
  3. Ask for one concrete piece of work. The model works on a copy and hands you a proposal.
  4. Read the proposal: the exact changes, and the check before and after. Apply it or reject it.
  5. After you apply it, read the record of what happened. A chat reply alone does not show that a change was saved.
  6. When you come back later, reload the application and check that the last result is still there.

Your first session walks through this cycle. StudyState, a study-plan template, gives a concrete example.

Update or move

Before you change an installation, write down the installed release, the application's identity and the template's source revision. Keep a verified backup outside anything you are about to replace. A template checkout, a container image or a conversation export is not a full backup.

Running the one-line install command of a newer release over an older install offers you an upgrade in place. You type upgrade, and your data is kept. There is still no way back to an earlier release: data saved by one release may not be compatible with another. Read the update boundary before you run it.

An imported template is a separate managed copy. Editing its original repository does not change your application.

Moving to another machine changes the environment. Tool availability, permissions, credentials and reachable services all need checking again. AI tools and portability explains what can travel with your work and what needs new setup.

Back up and recover

How it works. Every application has its own Back up now button. A backup is an archive of the files of that application. Restoring one creates a new application from the backup. It never overwrites the application you already have, so you can compare the two and keep the one you want.

What a backup contains. The files of the application. It does not include the application's Git history, its conversations, the index of records or the approvals you gave. A restore recreates files only: it does not finish interrupted work, and it does not check what happened outside StatePort.

Before a backup

  • Finish or check outstanding changes, so you know which state you are keeping.
  • Write down the application's identity and a few facts you expect to get back, such as the current project step or your last study reflection.
  • Use Back up now and check the backup status and its record. A backup attempt is not the same as a stored archive.
  • Keep backups private. The check on a backup tests its integrity. It is not encryption, and there is no schedule or retention policy.

Restore a separate instance

  1. Pick the backup you want. Check which application and which point in time it represents.
  2. Review the new application's name and any source-access details. Do not assume that earlier permission carries over to a new application.
  3. Apply only the plan you reviewed. If the plan expires, or the backup, the source or the destination changes, prepare and review a new plan.
  4. Check the restore record and open the new application. Compare it with the facts you wrote down before the backup.
  5. Check the model route separately, if the new application uses one. Keep the original application until you have checked the restored work and decided which copy to use.

If a restore stops with an uncertain result, keep the record and both applications so you can look at them. Do not remove the destination, and do not apply the same restore again and again. See troubleshooting.

What recovery does not undo

A restore puts files back. It does not recall a sent message, reverse a payment, remove a remote deployment or undo a request that already reached a model provider. Check outside effects yourself before you carry on. A restored file that says “not sent” does not prove the message was never sent.
