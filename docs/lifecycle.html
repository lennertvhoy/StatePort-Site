Set up a known release

Keep three things apart: StatePort itself, the template that defines an app, and your instance, which holds your actual work. Replacing StatePort does not back up your instance. Importing a newer template does not update your existing work.

To install the current release, follow getting started and check the release status. Keep the install receipt and the address the installer printed. Updates and removal says what this alpha supports for updating and removing StatePort.

Use the application

  1. Open the app you want and read its current state before you ask for anything. Two instances from the same template hold different work.
  2. Pick one concrete task. Readiness tells you whether the app can do it with the tools and permissions it has now.
  3. Review the proposed change before you apply it. Check the target, the files or facts it touches, and the access it asks for.
  4. After you apply it, check the receipt and the updated state. A chat reply alone does not show that a change was saved.
  5. When you come back later, reload the app and check that the last result is still there. Use Activity and Receipts to settle any doubt before you repeat a request.

The everyday-work guide walks through this cycle. StudyState, a study-plan template, gives a concrete reflection example.

Update or move

Before you change an installation, write down the installed release, the app’s identity and the template’s source revision. Keep a verified backup outside anything you are about to replace. A template checkout, a container image or a conversation export is not a full backup of an instance.

Updating StatePort in place is not supported in this alpha. Read the update boundary before you re-run an installer. An imported template is a separate managed copy. Editing its original repository does not change your instance.

Moving to another machine changes the environment. Tool availability, permission grants, credentials and reachable services all need checking again. The portability guide explains what can travel with your work and what needs new setup. Export and import exist for an instance’s files. Grants, receipts and provider logins do not travel, and there is no migration wizard.

Back up and recover

Availability: a verified backup and restore as a new instance were measured through the API on an installed Alpha.20. Restore from the interface does not work yet. Keep your own copy of anything you care about outside the Ubuntu distribution where StatePort runs. What you see depends on the app, its permissions and the installed version.

What a backup contains. A backup archives the instance’s files. It does not include the instance’s Git history, conversations, the receipts index or approvals. Restore creates a new instance from those files. It recreates files only. It does not finish interrupted work or check what happened outside StatePort.

Before a backup

  • Finish or check outstanding changes so you know which state you are keeping.
  • Write down the app’s identity and a few facts you expect to get back, such as the current project step or your last study reflection.
  • Where available, use Back up now and check the backup status and receipt. A backup attempt is not the same as a verified archive.
  • Keep backups private. Verification checks integrity. It does not mean encryption, a schedule or a retention policy.

Restore a separate instance

Restore makes a new managed instance. It does not overwrite the source app. In versions that show Settings → Backup & recovery, an operator picks an indexed backup, reviews the restore plan and the new instance’s identity, approves that exact plan, and applies it.

  1. Pick the backup you want. Check which app and which point in time it represents.
  2. Review the proposed new identity and any source-access details. Do not assume earlier consent carries over to a new instance.
  3. Apply only the plan you reviewed. If the plan expires, or the backup, the source or the destination changes, prepare and review a new plan.
  4. Check the restore receipt and open the new app. Compare it with the facts you wrote down before the backup.
  5. Check tool readiness and permissions separately. Keep the original instance until you have checked the restored work and decided which copy to use.

If recovery stops with an uncertain result, keep the receipt and both instances so you can look at them. Do not remove the destination or apply the restore again and again to make an error go away. See troubleshooting.

What recovery does not undo

Recovery restores files. It does not recall a sent message, reverse a payment, remove a remote deployment or undo a provider request. Check outside effects yourself before you carry on. A restored file that says “not sent” does not prove the message was never sent.

Current availability

The release status page says what you can install. The controls described here may be missing in an older install or for a particular template. Do not use developer commands or manual file replacement to get around a missing recovery control. Keep the original work and report what is missing.
