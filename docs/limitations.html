StatePort is in early alpha. Do not use it for important data. Use a computer or virtual machine where a mistake would not matter, use test data, and keep your own backups.

Exact status statement (for reviewers)

StatePort 0.1.0-alpha.22 is the current signed release. It installs and passes in a clean test VM; real-Windows and reboot results pending. In a fresh Windows 11 test virtual machine with WSL2 and stock Ubuntu 24.04, the Alpha.22 installer, run from a local copy of the signed files with the container images pulled from the registry, installed StatePort. All services reported healthy, the web page and the API answered, and a second run of the installer over the finished install reported that it was already installed and changed nothing. Alpha.22 was installed on that test machine three times: the first run stopped while downloading the images, which had not been uploaded yet (a mistake in the test setup), and the second and third runs finished healthy. The public one-line route was not used for those installs. The installed keep-alive task was registered to start at Windows start-up, at sign-in and every 10 minutes, but it had not run on the test machine. Reboot: not measured. Uninstall was not run on Windows. The study sample in the browser, undo, export and import, backup and restore, and template import were last measured on Alpha.21 and have not been repeated on Alpha.22. On Alpha.21, coding-agent runs, chat replies, restore from the interface, the workbench terminal and files tools, per-application workspaces, and the standing-authority and updater pages did not work, and none of that has been measured on an installed Alpha.22.

Early alpha

StatePort is an early alpha. Alpha.22 is a test release for people who want to try it and report what breaks. This page has three lists: what works today, what is not working yet, and what is designed but not built. Only the install checks on a test virtual machine and the Linux checks of the Alpha.22 code were measured on Alpha.22; the rest of the first two lists was measured on Alpha.21 and has not been repeated on Alpha.22.

The one supported setup

  • Windows 11 (build 22000 or newer) on an AMD64 (x86-64) computer.
  • WSL2, not WSL1, with stock Ubuntu 24.04 and systemd running as the first process.
  • A normal Ubuntu user with sudo, not the root account.

WSL1, ARM64, macOS, Docker Desktop, native Linux, Windows 10 and other Linux distributions are not supported. The installer checks your setup before it changes anything and stops with a message if it does not match. See platform support.

What works today

This list has two parts: what was measured on Alpha.22, and what was measured on Alpha.21 and has not been repeated on Alpha.22. Both were measured on fresh Windows 11 test machines (virtual machines) with WSL2 and stock Ubuntu 24.04, except where a Linux check is named. Something that was measured only on Alpha.20 is not in this list.

Measured on Alpha.22

  • Install in a clean test VM. Alpha.22 was installed three times on a fresh Windows 11 virtual machine with WSL2 and stock Ubuntu 24.04, reset to a clean snapshot each time. The first run stopped while downloading the container images, because they had not been uploaded to the registry yet; that was a mistake in how the test was set up. The second and third runs finished and came up healthy. These installs ran from a local copy of the signed files, with the images pulled from the registry. They did not use the public one-line command, and the install time was not recorded.
  • What the installed product answered. After the third install every service reported healthy, the web page answered with the StatePort page, and the API answered its readiness check. The API answered on port 18561 while the install plan had named 18578. This was looked into: the installer picks ports twice during one install, and each pick checks which ports are in use at that moment, so the two picks can differ by one step. The installer then uses the port the started service really listens on, and the API answered on that one. Nothing in the browser depends on the planned port. Because the notice about this is only printed in verbose mode, you will not see it in a normal install transcript.
  • Running the installer again. A second run over the finished install reported that StatePort was already installed and wrote no second install receipt. The web page and the API still answered afterwards.
  • What the installer prints. It looks for an existing OpenCode sign-in and says what it found (on the test machine: none found, nothing copied), gives the address to open and the path of the install receipt, and lists how to stop and remove StatePort (your data is kept) and how to reinstall it.
  • The keep-alive task, as registered. Windows listed the StatePortKeepAlive task with three triggers: at Windows start-up, at sign-in, and every 10 minutes. It was set to run when nobody is signed in, to run on battery power, to have no time limit and to restart if it fails. It had never run on the test machine, so whether it keeps StatePort reachable is not measured.
  • Linux checks of the Alpha.22 code (not an install of the signed release on Windows). The project’s own end-to-end check ran 50 scenarios against the Alpha.22 source code on a Linux development machine: 40 worked, none was found broken, 1 could not be tested (the updater page, which needs an installed updater) and 9 were not run (they need an AI provider sign-in). The 40 include the workbench terminal and files tool, the standing-authority page, backup and restore through the interface, and a coding-agent run with a stand-in model instead of a real AI model. A separate lifecycle check of the installer, in a Linux container that imitates WSL2, passed 10 of 10 steps: install, run again, refusing without a flag, asking on a terminal, reinstall, refusing a different release, uninstall (data kept), install again (data comes back) and purge (data deleted). That check used Alpha.21 container images and a test signing key.

Measured on Alpha.21, not repeated on Alpha.22

  • Install of Alpha.21. The one-line command installed Alpha.21 and it came up healthy on 2 of 3 fresh install attempts. On the public route, one attempt installed in about 12 minutes. The other was refused after about 5 minutes by a package check that races Ubuntu’s background updates (see troubleshooting); nothing it left behind blocked the next try. A separate install from a local copy of the same signed files also came up healthy, in about 18 minutes.
  • What a good install prints. StatePort is installed and healthy., then Open StatePort at: http://127.0.0.1:<port>/, then the path to an install receipt under ~/.local/state/stateport-install/receipts/. The port number varies, for example 18216. Afterwards four services were running and healthy: the web interface, the API, the worker and the execution host, and the install receipt recorded a successful result.
  • The first screen. A fresh install opens on an empty first screen with one main button, Open the study sample. Worker execution shows as disabled and the provider as not configured, each with a short explanation: the study sample works without either. That is normal, not a broken install.
  • The study sample in the browser. The web interface opens without a login. One click on Open the study sample installs the bundled sample and opens it after about 10 seconds. You can start an activity, review the exact change, approve it, write a reflection, review what saving it does, apply it, and open the receipt. The Receipts tab lists the history. The saved state was still there after a reload. A fixed script proposes the changes in the sample, not an AI model.
  • Going back from a review. It withdraws the proposed change. No pending approval is left behind. On Alpha.20 it left one.
  • The notifications list. It opens and lists real items, such as a reminder that no verified backup exists yet. On Alpha.20 it did not open.
  • Backup from the interface. Back up now produced a verified backup receipt, and the recovery panel loads. On Alpha.20 the panel showed an error.
  • Templates. A ProjectState and a StudyState checkout placed in the import folder by your normal Ubuntu user were listed, inspected, approved and installed as separate managed copies, both through the browser (Catalog, then Import a repository) and through the API, without any ownership fix. The read-only inspect action ran, and the source repository was not changed. A stale inspection and an approval with the wrong digest were refused. On Alpha.20 this needed a one-time ownership fix. A template upgrade to a newer revision also worked through the API, and was refused until it was approved.
  • Safe refusals. A change prepared against outdated state is refused and nothing is changed, although the error message is vague.
  • Undo, export, backup and restore through the API. Undoing the last evidence update returned the saved state to exactly what it was before. An export imported as a new instance with the same state, and an import whose archive fingerprint did not match was refused. A verified backup restored as a new instance. Receipt and proposal checksums were recomputed independently and matched.
  • Restarts. Restarting the API service and the worker service each took about 2.4 seconds to come back, with the saved state unchanged. The test machine also restarted once without warning; afterwards the saved study state was intact and every instance was still listed.
  • The local API. It refused requests without a token, with a wrong identity or from another website.
  • The provider screen. It shows the selected provider and whether OpenCode is installed, and it refuses a model name with an invalid shape before sending it.
  • Memory and disk at idle. The four installed services used about 83 MB of memory together, and the Ubuntu environment about 0.65 GB in total. The container images take about 2.2 GB on disk. Use under real work is not measured.

The installer is a script you can read. It checks that you have WSL2 (not WSL1), Ubuntu 24.04, systemd as the first process, Windows build 22000 or newer, powershell.exe reachable from Ubuntu, an x86-64 CPU, and a user that is not root. It asks for two typed confirmations. It has two options that install nothing: --transport-probe and --materialization-preflight. Getting started explains them.

Not working yet

This list has three parts. First, what was measured as failing or rough on Alpha.21. Second, what failed on Alpha.20 and has not been checked again on Alpha.21 or Alpha.22. Third, what has not been measured at all. Several items in the first part passed in the Linux checks of the Alpha.22 code listed above (the terminal and files tool, the standing-authority page, restore through the interface, a coding-agent run with a stand-in model). That is not a measurement of an installed Alpha.22 on Windows, so they stay on this list.

Failed or rough on Alpha.21, not measured again on an installed Alpha.22

  • A package check can stop the install. The installer refused one of three fresh Alpha.21 attempts with package_installation_invalid, because its last check raced Ubuntu’s background updater. Waiting a minute and running the same command again is the way round it. The Alpha.22 test installs did not meet it, but they were few and did not use the public route. See troubleshooting.
  • Coding-agent runs. A run is refused before it starts. The readiness check now names the missing provider files, but nothing in StatePort can create them: an administrator has to place them in a read-only provider folder, and there is no agent workspace.
  • Chat replies. The Conversation tab opens and a message is accepted. An assistant attempt starts, but it fails at the provider call, because no AI provider could be connected. What application state the assistant is given could not be checked.
  • Provider actions. On the test machine, checking the selected adapter and saving an API key were refused with “provider action access denied”. The cause is not known. Through the API, the adapter check worked.
  • Restore from the interface. Plan restore is now reachable, but it fails with “A request value could not be used”. Through the API the same request fails unless it includes a destination name, as on Alpha.20.
  • The Learning tab. After a change was applied, it still showed the old numbers until the page was reloaded. The backup panel likewise kept saying “Backup due” and “Last backup: never” after a verified backup.
  • Slow and stale screens. Opening the study sample took about 10 seconds, some controls stayed greyed out for about 8 seconds more, and the Applications list kept saying no applications existed until a reload.
  • Vague error messages. A refused change reports only that worker execution terminated. Other failures report that a request value could not be used, without naming the value.
  • The standing-authority and updater pages. Both still answer with errors, in the interface and through the API.
  • The terminal and files tools in the workbench. The terminal opens and closes at once with “terminal_output_refused”, and creating a file is refused (“path is not classified by the application policy”). The Files tab shows no files for an imported ProjectState. On Alpha.20 they failed too.
  • Per-application workspaces. Every one is unavailable until an administrator issues authority from a shell with sudo.
  • The background worker. It runs and reports healthy, but it does not run any jobs. The governed runs of the sample happen in the web service.
  • The Governed runs tab. It reports that governed execution is degraded. The coding-agent engines (pi, Codex and OpenCode) are listed as unavailable. Starting a run by hand needs a plan digest typed in as text, so the study screen is the usable path.
  • The Synthetic reference app. It is still listed as unavailable in the Catalog.
  • Keeping WSL running. The installer registers a Windows scheduled task called StatePortKeepAlive that is meant to keep Ubuntu running after you close the last WSL window. On Alpha.21 it had never run on the test machine, because it only started at a Windows sign-in. After the Alpha.21 test machine restarted without warning and nobody signed in, the task did not start, StatePort stayed down until Ubuntu was started by hand, and it answered again about two minutes later. The Alpha.21 task was also set not to start on battery power. The Alpha.22 task is registered differently (start-up, sign-in and every 10 minutes, run when nobody is signed in, run on battery), but it had not run on the test machine either, so none of this is measured on Alpha.22.

Failed on Alpha.20, not checked again on Alpha.21 or Alpha.22

  • Recreating the application container and reading its logs. Both were refused on Alpha.20. The buttons are still there on Alpha.21, but they were not pressed.
  • Cancelling an approved-but-stale run. The cancel button was refused, and the run stayed listed as approved.
  • A leftover archive from an earlier install attempt. It can make the installer refuse with image_archive_conflict. The troubleshooting page has the workaround.

Not measured

  • Windows reboot. A planned reboot was not measured on Alpha.21 or Alpha.22 (reboot: not measured). The test machine cannot reboot its nested WSL.
  • Uninstall on Windows. Not run on Windows. The Alpha.22 installer offers options to uninstall (data kept), install again and purge, and they passed in the Linux lab described above, which is not a Windows measurement.
  • Undo in the browser. The attempt on Alpha.21 did not finish, because the test machine stalled. It was not tried on Alpha.22.
  • Restarting the web service. It was not restarted on purpose.
  • Stopping. Whether the product keeps running after you close the last Ubuntu window was not measured on Alpha.21 or Alpha.22. On Alpha.20 it stopped and came back about three minutes after Ubuntu was reopened.
  • A real AI provider request. No provider could be connected.

The measured installs ran on virtual machines, not on a physical laptop. Something not measured may work or may not. That is not known yet.

Designed, not built

These appear in the design, in these docs or in the papers. They are not part of Alpha.22.

  • Undo for most changes. One undo exists: the last evidence update in the StudyState sample. Most changes cannot be undone. Alpha.22 does not support rolling back the platform, and its release file says so.
  • A chat assistant that reads your state. The chat assistant sees only the recent conversation. It does not read your study or project files. Actions that go through StatePort’s approval steps get a small bundle of information built from the saved state. Chat does not.
  • Saving coding-agent output into your app’s state. For actions that follow a fixed script, such as the StudyState sample, StatePort applies what you approve. Output from coding agents is recorded as a run result. StatePort does not turn it into saved state.
  • Backup of history and receipts. A backup archives the instance’s files. It does not include Git history, conversations, the receipts index or approvals. Restore creates a new instance from those files. It does not finish interrupted work or check what happened outside StatePort.
  • Moving to another machine. Export and import work for an instance’s files. Grants, receipts and provider logins do not travel, and there is no migration wizard.
  • Guided flows for imported templates. An imported ProjectState or StudyState is checked and stored as a separate copy with one inspection action. The step-by-step flows exist only in the StudyState sample. StudyState’s next-activity engine, the part that picks what to study next, is not part of StatePort.
  • Signed receipts. Receipts carry a checksum of their content. They are not individually signed.
  • A general background worker. The worker runs one fixed kind of container job. Agent runs and chat are tracked by the web service.

Local use

  • StatePort is for one person on one local computer.
  • There is no hosted service, no team accounts and no supported way to reach it over a network.
  • The address it prints works on that computer only. Do not expose it to the internet.
  • The interface and the docs are in English only.

Security

  • StatePort has not had an independent security review or penetration test.
  • The installer uses sudo and changes the Ubuntu distribution it runs in. Use a distribution or virtual machine you can afford to lose.
  • StatePort makes no legal or regulatory compliance claims.

Applications and features

  • StudyState (a study-plan template) and ProjectState (a project-tracking template) are early alpha. They are not finished, and nobody independent has evaluated them.
  • Imported templates must be Git repositories under an import folder the installer creates, and only committed content is copied into the managed app. That is how it is built. On Alpha.20 a source repository with uncommitted changes imported only its committed files; that was not checked again on Alpha.21 or Alpha.22. Alpha.20 needed a one-time ownership fix before a checkout appeared; Alpha.21 listed and inspected one without it, and Alpha.22 was not checked. See templates and troubleshooting.
  • There is no supported in-place update or rollback. See updates and removal.
  • StatePort is set up to use OpenCode as its coding agent: on Alpha.21 the first screen says to choose OpenCode and save a model, and the Runs tab lists OpenCode as not available yet. Codex is not bundled, and its program is not installed. StatePort does not check OpenCode’s login for you, and the first screen shows authentication as unverified. A real provider request was not measured, and the provider screen was not checked on Alpha.22.
  • Container deployment is a design preview and is not part of what the installer sets up. Cloud deployment and managed hosting do not exist.
  • Agent Kits (shareable app packages) are an idea and do not exist yet.
