What ProjectState is

ProjectState keeps a project’s human-owned outcome, current slice, working rules, and evidence in ordinary files. It helps an agent or team answer: what are we trying to change, what is the one active unit of work, what did we actually observe, and what should happen next?

An instance is a repository with its own project truth. A template is a reusable mold. StatePort supplies a managed application around the reviewed repository; it does not become the project’s authority and it does not replace the repository’s own checks.

The ProjectState v6 files

File or folderPurpose
PROJECT.mdThe outcome, scope, non-goals, and boundaries.
STATE.yamlOne current slice, its journey, status, blockers, and next action.
AGENTS.mdRules for making changes and keeping them safe.
evidence/<slice-id>/summary.mdEnvironment, command, result, artifacts, limitations, and what remains unrun.
scripts/projectstate_gate.pyA consistency check over the recorded outcome.

The gate checks what the record says; the real journey supplies the observed result.

Import and review in StatePort

  1. Open Catalog, then choose Import a repository.
  2. For a local source, place the Git checkout in the configured import folder, including its .git directory. For a public source, enter its HTTPS URL and exact 40-character commit.
  3. Choose the candidate and let StatePort perform a read-only inspection. Repository code is not executed during inspection.
  4. Review the template detection, source identity, commit, working-tree findings, and any inspection errors. Commit the version you intend to use before this step.
  5. Approve the unchanged inspection. A ProjectState template receives Create isolated copy; an ordinary unsupported repository can only be explicitly registered.
  6. After StatePort reports success, open the application or its durable import receipt. The service rereads the application and receipt before presenting that success.

If the source changes after inspection, the approval is stale and must be inspected again. This is the boundary that keeps the managed copy tied to what you reviewed.

Use it while developing

Suppose you are adding a template import. Put the outcome in PROJECT.md: “a new user can import a committed repository and open its managed copy.” Set STATE.yaml to the one slice that implements that journey. After the change, record the exact environment, command, observed import result, receipt, and remaining gaps in evidence/<slice-id>/summary.md. The next action should name the smallest unresolved step.

For a bug, the current slice might say “repair stale approval after the source commit changes.” The evidence should show the focused reproducer, the repair, and the rerun. A ProjectState instance can guide StatePort work while the managed application supplies the files, terminal, approvals, orchestration, and receipts that its adapter exposes.

Use it while operating the project

After release, the same instance can track an operating outcome such as “the public installer points to the signed artifact and the service recovers after restart.” The current slice can be “investigate a failed health check,” with the incident command, service logs, affected version, and recovery result in its evidence summary. The next action might be “reproduce on the supported environment,” “publish a corrected artifact,” or “monitor the external dependency.”

Development and operation use the same files because both need a visible outcome, one current slice, observed evidence, and an explicit next action. The instance does not gain a separate UI mode; you define the operating outcome and checks in the project contract.

Validation is evidence; acceptance is a decision

Run the smallest representative journey first, then the affected integration, then installed or release proof when the change crosses that boundary. Record the exact environment and limitations. A test can show that a parser accepts a file; a real journey shows whether the user can complete the outcome. A receipt shows what StatePort observed at one boundary.

The project owner still decides whether that evidence satisfies the outcome. Keep the observed result, the limitation, and the next action visible when the evidence is incomplete.

Limits and recovery

  • A ZIP without Git history cannot establish the required exact commit identity for template import.
  • A dirty or changed source is not silently folded into an approved copy; commit and inspect again.
  • ProjectState does not make arbitrary repository commands safe, and a template cannot grant itself capabilities StatePort has not implemented.
  • Backups, restore plans, restart behavior, and receipts belong to the installed product journey. Do not infer them from this repository’s files alone.
  • If a StatePort operation becomes uncertain, reread Catalog, Applications, or Receipts before retrying a mutation. The UI is designed to retain uncertainty instead of claiming success.
