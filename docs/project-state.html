ProjectState: a template for tracking a project

ProjectState is a set of plain files that describe a project: its goal, the one piece of work in progress, the working rules and the evidence. StatePort can inspect a committed ProjectState repository and store a separate copy of the exact snapshot you reviewed.

What ProjectState is

ProjectState keeps a project’s goal, the one piece of work in progress, the working rules and the evidence in ordinary files. It helps an agent or a team answer four questions: what are we trying to change, what is the one thing we are working on, what did we actually see, and what happens next? The template calls that one piece of work a “slice”.

An application is a repository with its own project truth. A template is a reusable starting copy. StatePort wraps a reviewed repository in a managed application. It does not become the authority for the project, and it does not replace the repository’s own checks.

The ProjectState files

File or folderPurpose
PROJECT.mdThe outcome, scope, non-goals and limits.
STATE.yamlThe one piece of work in progress (the current slice), the real user task that tests it, its status, blockers and next action.
AGENTS.mdRules for making changes and keeping them safe.
evidence/<slice-id>/summary.mdEnvironment, command, result, artifacts, limits, and what was not run.
scripts/projectstate_gate.pyA script that checks that the recorded outcome is consistent.

The check script reads what the record says. It does not run your project. A real run of the user task supplies the observed result.

The three actions

Once a ProjectState application is open, it offers three actions.

  • Set up project (from your own words). You describe the project in your own words, and the application builds the starting files from that description: the outcome in PROJECT.md, the current work in STATE.yaml, and the rules in AGENTS.md. It works on a copy, so you see the whole change before anything is written. Apply it if it says what you meant; reject it and try again with clearer words.
  • Do the next action. The application looks at STATE.yaml, works out the next step, and proposes the change that step needs. The proposal is a diff: the exact lines that would be added or changed, with the check’s verdict before and after. Apply it and it becomes one commit in the application. Reject it and nothing changes.
  • Check. This runs the check script on your files. It answers passed, not yet, or invalid, and tells you why. It is deterministic: it reads the files and compares them with each other. It never asks a model and never changes anything.

Two of the three actions need a model, so they need an AI route. Models and keeping up explains how to get one, including a route that needs no account. The check works either way.

Import and review in StatePort

  1. Open Catalog, then choose Import a repository.
  2. For a local source, put the Git checkout, with its .git folder, in /var/lib/stateport/imports. For a public source, enter its HTTPS URL and the exact 40-character commit.
  3. Choose the repository and let StatePort inspect it. The inspection only reads. It does not run repository code.
  4. Look at the detected template type, the source, the commit, any working-tree findings and any errors. Commit the version you want before this step.
  5. Approve the unchanged inspection. A ProjectState template gets Create isolated copy. An ordinary repository that is not a template can only be registered.
  6. When StatePort reports success, open the application or its import record. The service reads the application and the record again before it shows success.

If the source changes after the inspection, the approval is stale and you must inspect again. That keeps the managed copy tied to what you reviewed.

Use it while developing

Say you are adding a template import. In PROJECT.md you write the outcome: “a new user can import a committed repository and open their own copy.” You set STATE.yaml to the one piece of work that delivers it. After the change, you record in evidence/<slice-id>/summary.md the exact environment, the command, the import result you saw, the record of it and what is still missing. The next action names the smallest step left.

For a bug, the current work might be “repair the stale approval after the source commit changes.” The evidence should show a test that reproduces it, the repair and the rerun. A ProjectState application can guide StatePort work. What the managed copy offers is what StatePort’s ProjectState support provides.

Use it while operating the project

After release, the same application can track an operating outcome such as “the public installer points to the signed release and the service recovers after a restart.” The current work might be “investigate a failed health check”, with the incident command, service logs, affected version and recovery result in the evidence summary. The next action might be “reproduce on the supported setup”, “publish a corrected release” or “watch the outside dependency”.

Development and operation use the same files. Both need a visible outcome, one current piece of work, observed evidence and an explicit next action. There is no separate operating mode. You define the operating outcome and its checks in the project files.

Tests are evidence; acceptance is your decision

Run the smallest realistic test of the user task first, then wider tests, then a check on the installed or released product when the change reaches that boundary. Record the exact environment and the limits. A test can show that a parser accepts a file. A real run shows whether a user can finish the task. The record of a run shows what StatePort observed at one step.

The project owner still decides whether the evidence meets the outcome. When the evidence is incomplete, keep the observed result, the limit and the next action in view.

Limits and recovery

  • A ZIP file has no Git history, so it cannot give the exact commit that import needs.
  • A dirty or changed source is not silently merged into an approved copy. Commit it and inspect again.
  • ProjectState does not make arbitrary repository commands safe, and a template cannot give itself access that StatePort has not built.
  • Backups, restore, restart behaviour and records belong to the installed product. Do not infer them from a repository’s files alone.
  • If a StatePort operation becomes uncertain, read Catalog, Applications or the records again before you retry a change. The interface is meant to show uncertainty instead of claiming success.
