Templates: ProjectState and StudyState.

A template is a reusable starting point for an application. StatePort is designed to take one from a Git repository, review it with you, and create a managed copy with its own history, leaving the original untouched.

What a template is

An application in StatePort has two parts. The template is the reusable part: its starting files, its rules, and the operations it supports. The instance is your own copy, with your saved work, permissions, and history. Two people, or two projects, can start from the same template and end up with different instances. Independent instances from the same template are demonstrated in source-tree tests; not yet on an installed product. Importing a template creates a new instance from an exact snapshot; it does not turn the source repository into your live application, and later edits to the source do not change an instance you already have.

Both templates below are ordinary Git repositories of readable files. The contract they define is useful without StatePort. StatePort's part is to validate a reviewed copy and store it as an isolated managed copy. For an imported ProjectState or StudyState that copy has an inspection action; the guided flows exist only in the StudyState Sample.

ProjectState

In plain terms: ProjectState keeps a project's goal, its one current piece of work, its working rules, and the evidence of what actually happened in ordinary files, so that a person or an AI agent can pick up the project without replaying old conversations. It answers four questions: what are we trying to change, what is the one active step, what did we observe, and what should happen next?

The files are PROJECT.md for the outcome and boundaries, STATE.yaml for the current step, AGENTS.md for the rules, an evidence folder for results, and a small check script. Read the ProjectState guide for the details.

StudyState

In plain terms: StudyState keeps a learner's targets, activities, sources, sessions, reviews, and evidence in readable files, so progress is kept outside a chat window. Its next-activity engine belongs to the StudyState template and is not surfaced in StatePort. In the StudyState Sample, changes to that record are proposals you review before they are saved.

The StudyState Sample is a small worked example of that loop. You start an activity, review the exact change, approve it, write a reflection, review what saving it would do, apply it, open the receipt, and reload to see the result still there. The Sample offers a fixed set of activities, and its loop passes in the project's automated tests. That is the flow shown on the home page and in the field guide video. Read the StudyState guide and your first session for the steps.

Other templates

StatePort is designed to accept any repository that declares a valid template manifest and supported actions, called a portable StateSpec repository, and to run only the actions it has actually implemented. Declaring a capability in a repository does not grant it. Nothing on this page says that a third template has been tried on an installed Alpha.20.

How import is designed to work

This is design intent. It comes from the product's design and has not been measured on an Alpha.20 install.

  1. Put a real Git checkout, including its .git folder, below the import folder the installer creates. The default is /var/lib/stateport/imports. A ZIP file without Git history cannot identify an exact commit. You may instead give a public HTTPS repository and its full 40-character commit.
  2. In StatePort, open Catalog and choose Import a repository.
  3. Choose Inspect. Inspection only reads. It reports the source, which template it detected, the commit, and whether the working tree has uncommitted changes.
  4. Read the findings. If the repository is dirty or reports an error, fix it, commit, and inspect again.
  5. Name the application and approve that exact inspection.
  6. For a supported template, choose Create isolated copy. For an ordinary repository that is not a supported template, the action is Register repository.
  7. Open the new application or its install receipt.

Your approval is tied to what was inspected. If the source changes afterwards, the approval is refused instead of silently importing a different version.

What is verified and what is not

  • The install itself: measured on Alpha.20. It installed and reported healthy on a fresh Windows 11 virtual machine with WSL2 and Ubuntu 24.04, five times. See current limitations.
  • The StudyState sample flow: implemented and passing in the project's automated tests, and shown in the product recordings on this site, made before Alpha.20. It has not yet been run end to end on an installed Alpha.20.
  • Importing a ProjectState or StudyState repository: not measured on the installed product.
  • A third, independent template: not measured.

Not measured means we do not know yet, not that it fails. If you try it, tell us what happened.

What StatePort is designed to copy and run

  • The source repository is only read and stays untouched.
  • The managed copy is made from the exact snapshot you reviewed, with its own identity and record of where it came from.
  • Repository code is not executed while StatePort discovers or inspects a repository.
  • Only actions that StatePort itself implements for the detected template are available, and application actions go through review, approval, and a receipt. For an imported ProjectState or StudyState the implemented action is an inspection.

If a repository does not appear

These are design-based checks that have not been measured on Alpha.20 yet:

  • The checkout should be below the import folder, be a real directory rather than a symbolic link, and keep its .git folder.
  • Refresh the list after copying a checkout in.
  • For a public source, use HTTPS and a full commit, not a branch name.
  • If inspection reports uncommitted changes or an invalid template, make the smallest fix, commit it, and inspect again.
  • If an import response is uncertain, reread Catalog and Receipts before you try again.

See platform support for the supported setup, getting started to install, and current limitations for what has not been measured.
