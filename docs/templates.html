Templates: ProjectState and StudyState.

A template is a reusable starting point for an app. StatePort takes one from a Git repository, shows it to you for review, and makes a managed copy with its own history. The original stays untouched.

What a template is

An app in StatePort has two parts. The template is the reusable part: its starting files, its rules and the operations it supports. The instance is your own copy, with your saved work, permissions and history. Two people, or two projects, can start from the same template and end up with different instances. The project’s automated tests show that instances made from the same template stay independent. On an installed Alpha.20 I imported the same ProjectState template twice and got two separate instances. Importing a template makes a new instance from an exact snapshot. It does not turn the source repository into your live app, and later edits to the source do not change an instance you already have.

Both templates below are ordinary Git repositories of readable files. You can use them without StatePort. StatePort checks a reviewed copy and stores it as a separate managed copy. For an imported ProjectState or StudyState that copy has one inspection action. The step-by-step flows exist only in the StudyState sample.

ProjectState

In plain terms: ProjectState is a template for tracking a project. It keeps the goal, the one piece of work in progress, the working rules and the evidence of what happened in ordinary files, so a person or an AI agent can pick the project up without replaying old conversations. It answers four questions: what are we trying to change, what is the one thing we are working on, what did we see, and what happens next?

The files are PROJECT.md for the outcome and limits, STATE.yaml for the current work, AGENTS.md for the rules, an evidence folder for results, and a small check script. The ProjectState guide has the details.

StudyState

In plain terms: StudyState is a template for a study plan. It keeps a learner’s targets, activities, sources, sessions, reviews and evidence in readable files, so progress is kept outside a chat window. Its next-activity engine, the part that picks what to study next, belongs to the template and is not part of StatePort. In the StudyState sample, changes to the record are proposals you review before they are saved.

The StudyState sample is a small worked example. You start an activity, review the exact change, approve it, write a reflection, review what saving it does, apply it, open the receipt, and reload to see the result still there. The sample offers a fixed set of activities, and its loop passes in the project’s automated tests. The home page and the field guide video show this flow. The StudyState guide and your first session have the steps.

Other templates

StatePort is meant to accept any repository that declares a valid template file and supported actions. That format is called a portable StateSpec repository. StatePort runs only the actions it has actually built, and a repository cannot give itself access by declaring it. I have not tried a third template on an installed Alpha.20.

How import works

I measured this flow on an installed Alpha.20 with local checkouts of ProjectState and StudyState.

  1. Put a real Git checkout, with its .git folder, in the import folder the installer creates. The default is /var/lib/stateport/imports. A ZIP file has no Git history, so it cannot give an exact commit. Or give a public HTTPS repository and its full 40-character commit.
  2. In StatePort, open Catalog and choose Import a repository.
  3. Choose Inspect. Inspection only reads. It reports the source, the template type it detected, the commit, and whether the working tree has uncommitted changes.
  4. Read the findings. If the repository is dirty or reports an error, fix it, commit, and inspect again. In my test a dirty repository still imported, but only its committed files.
  5. Name the app and approve that exact inspection.
  6. For a supported template, choose Create isolated copy. For an ordinary repository that is not a supported template, the action is Register repository.
  7. Open the new app or its install receipt.

Your approval is tied to what was inspected. If the source changes afterwards, StatePort refuses the approval instead of quietly importing a different version. In my test, an inspection made stale by a changed source was refused.

Ownership. A checkout placed in the import folder by your normal Ubuntu user will not appear, or inspection is refused, until you change its owner to the service user once: sudo chown -R stateport-control:stateport-control /var/lib/stateport/imports/<repository>. Troubleshooting has the full entry. After that fix, import, inspect and install all worked in my tests.

What is verified and what is not

  • The install itself: measured on Alpha.20. It installed and reported healthy on seven fresh Windows 11 test installs with WSL2 and Ubuntu 24.04. See current limitations.
  • The StudyState sample flow: measured end to end in the browser on an installed Alpha.20, including undo and the saved state kept after restarts.
  • Importing a ProjectState or StudyState repository from a local checkout: measured on an installed Alpha.20. Discover, inspect, plan, approve, install and the read-only inspect action all worked. A stale inspection was refused, and a dirty source repository imported only its committed files. The source repository stayed untouched.
  • Importing from a public HTTPS repository: not tested.
  • A third, independent template: not tested.

Not tested means I do not know yet, not that it fails. If you try it, tell me what happened.

What StatePort copies and runs

  • The source repository is only read. It stays untouched.
  • The managed copy is made from the exact snapshot you reviewed, with its own identity and a record of where it came from.
  • Repository code is not run while StatePort finds or inspects a repository.
  • Only the actions StatePort has built for the detected template are available, and app actions go through review, approval and a receipt. For an imported ProjectState or StudyState, the action that exists is an inspection.

If a repository does not appear

These are the checks that mattered in my tests.

  • The checkout should be in the import folder, be a real directory and not a symbolic link, and keep its .git folder.
  • If a checkout you copied in does not appear, or inspection is refused, its ownership is the usual cause; see the entry in troubleshooting.
  • Refresh the list after you copy a checkout in.
  • For a public source, use HTTPS and a full commit, not a branch name.
  • If inspection reports uncommitted changes or an invalid template, make the smallest fix, commit it, and inspect again.
  • If an import response is uncertain, read Catalog and Receipts again before you try again.

See platform support for the supported setup, getting started to install, and current limitations for what has not been measured.
