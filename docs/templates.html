Templates: a reusable starting point.

A template is a reusable starting point for an application. StatePort takes one from a Git repository, shows it to you for review, and makes a managed copy with its own history. The original stays untouched.

What a template is

An application in StatePort has two parts. The template is the reusable part: its files, its check and the actions it offers. The application is your own copy, with your own work in it. Two people can start from the same template and end up with two different applications.

Importing makes a new application from an exact snapshot. It does not turn the source repository into your live work, and later edits to the source do not change an application you already have.

The templates below are ordinary Git repositories of readable files. You can use them without StatePort. StatePort reads a reviewed copy and keeps it as a separate managed copy.

The three templates

ProjectState is a template for tracking a project. It keeps the goal, the one piece of work in progress, the working rules and the evidence in ordinary files, so that a person or an AI agent can pick the project up without replaying old conversations. Its public repository is lennertvhoy/ProjectState_Template. The ProjectState guide has the details.

StudyState is a template for a study plan. It keeps your targets, activities, sources, sessions, reviews and evidence in readable files, so progress is kept outside a chat window. Its public repository is lennertvhoy/StudyState_Template. The StudyState guide has the details.

Decision Log is an independent template that depends on neither of the other two. Every question that has to be settled gets an entry with a date by which it should be decided. When it is settled, the entry gets a short reason and a written record. Its public repository is lennertvhoy/StatePort-Source, on the branch templates/decision-log. To import it, put https://github.com/lennertvhoy/StatePort-Source in Public HTTPS repository and templates/decision-log in Branch, tag or commit (optional). Its own README describes the four actions: Check, List due, Draft the oldest open decision, and Add an open question.

There is also a bundled study sample that ships with StatePort, so you can try the loop before you import anything.

The template contract

Any repository can be imported if it follows the same contract as the templates above. A template declares five things:

  • Its state: the files that hold the work, in a Git repository.
  • Its outcome: what the work is for.
  • Its check: a deterministic check of those files that answers passed, not yet or invalid, with a reason. Never a model's opinion.
  • Its actions: named pieces of work, each either a check action (read-only) or an agent action (a model works on a copy).
  • Your grants: what may run, with which model, how much and until when.

StatePort offers exactly the actions a template declares, and nothing more. A template cannot give itself access to something StatePort has not built.

How import works

  1. Give StatePort the repository, in one of two ways. Put a real Git checkout, with its .git folder, in the import folder the installer creates; the default is /var/lib/stateport/imports. A ZIP file has no Git history, so it cannot be used here. Or give a public HTTPS repository address in Public HTTPS repository.
  2. For a public repository, the second field, Branch, tag or commit (optional), can stay empty. Empty means the repository’s default branch. You can also type a branch or tag name, or a full 40-character commit.
  3. In StatePort, open Catalog and choose Import a repository.
  4. Choose Fetch and inspect for the public repository, or Inspect for a checkout in the import folder. Inspection only reads. It reports the source, the kind of template it detected, the commit, and whether the working tree has uncommitted changes.
  5. Read the findings. If the repository is dirty or reports an error, fix it, commit, and inspect again.
  6. Name the application and approve that exact inspection.
  7. For a template that follows the contract, choose Create isolated copy. For an ordinary repository that is not a template, the action is Register repository.
  8. Open the new application, or its record of the import.

StatePort resolves the name you typed once, to the exact commit it points to. The review screen shows that commit, and your approval and the import record are bound to it, so a later push to the same branch does not change an application you already imported. If the source changes between the inspection and your approval, StatePort refuses the approval instead of quietly importing a different version.

Ownership. A checkout placed in the import folder by your normal Ubuntu user is listed, inspected and installed without any ownership change. If a checkout does not appear on your install, troubleshooting has the entry.

What StatePort copies and runs

  • The source repository is only read. It stays untouched.
  • The managed copy is made from the exact snapshot you reviewed, with its own identity and a record of where it came from.
  • Repository code is not run while StatePort finds or inspects a repository.
  • A template may ship the code for its own check actions. That code runs only inside the sandbox: no network, a read-only copy of your files, a clean environment, a time limit and its own process.
  • The instructions of an agent action shape what the model is asked to do. They cannot widen what the model is allowed to do.

If a repository does not appear

  • The checkout should be in the import folder, be a real directory and not a symbolic link, and keep its .git folder.
  • Refresh the list after you copy a checkout in.
  • For a public source, use HTTPS. The branch, tag or commit field is optional: leave it empty for the default branch, or type a branch, a tag or a full 40-character commit.
  • If inspection reports uncommitted changes or an invalid template, make the smallest fix, commit it, and inspect again.
  • If an import result is uncertain, read Catalog and the records again before you try again.
